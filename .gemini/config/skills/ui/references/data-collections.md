# Record Collections and Quantitative Data

Apply the rules below when the interface renders repeated records or quantitative values compared across items, time, or totals.

## Attribute Capacity Between Primary View and Secondary Detail

- **When** displaying a collection of records in a single view, include in the primary view only the attributes needed to identify a record, compare records, and trigger the primary action, so the minimum total width required to render horizontal attributes intact does not exceed the container width; for wide 2D data tables on narrow viewports (`320px`), scroll the table horizontally inside its own container so the page itself never scrolls horizontally.
- **When** a record carries more attributes than fit horizontally in the primary container, keep the identifying and comparison attributes in the primary view and move the remaining detail attributes into a secondary disclosure view (drawer, detail pane, or expanded row) opened on selection.

## Column Alignment, Quantitative Integrity, and Repeated Row Action Weight

- **When** a data column displays quantitative magnitudes meant to be compared by place value across rows (or timers, counters, and prices), end-align the column (`text-align: end`) so digits of the same place value share a vertical axis and enable tabular numerals (`font-variant-numeric: tabular-nums`).
- **When** a data column displays strings read for character recognition rather than numeric magnitude comparison, start-align the column along the natural reading direction (`text-align: start`); if every value in the column shares a fixed character length (such as standardized identifiers or formatted timestamps), combine `font-variant-numeric: tabular-nums` (and `slashed-zero` on identifiers where `0` must be distinct from `O`) so corresponding characters align vertically.
- **When** the same fact appears in multiple places on a screen or an additive total or two-value difference is displayed alongside its component figures, bind repeated facts to one variable and compute additive sums and two-value differences from the displayed rounded component figures (using a consistent decimal precision per metric) so a reader checking the arithmetic on screen sees exact digit-for-digit agreement. *Guardrail*: Never hardcode duplicate facts separately across cards and charts, and never round an additive total or two-value difference independently from the rounded component figures shown beside it.
- **When** displaying a relative change or delta, state the comparison baseline in the same phrase, color the delta by whether the movement improves or degrades the metric's domain goal rather than by its mathematical sign, and render a zero change or a change from a zero prior baseline in neutral muted text (writing the absolute gain as `+N (new)` when the prior baseline was `0`, or a muted dash `—` when no prior baseline exists). *Guardrail*: Never display a bare delta without naming what period or target it is measured against, never color an unfavorable rise (such as higher error rate, latency, cost, or churn) in positive green or a favorable drop in negative red, and never render `+0`, `0.00%`, `+100%` from zero, or `>999%` in status color.
- **When** rendering a metric or table cell whose value is zero or unrecorded, format a measured zero with its numeric unit and precision (`0`, `$0.00`, `0.0%`) and render an unrecorded or inapplicable cell value as a muted em dash (`—`) with an accessible name stating that no value is recorded. *Guardrail*: Never conflate a measured `0` with a missing value, and never print raw code literals (`null`, `undefined`, `NaN`), text placeholders (`N/A`), or an unlabeled blank cell for a missing value.
- **When** each row in a list or table carries row-level actions, demote all per-row actions to outlined, ghost/text, or overflow-menu controls, and respond to row hover or action reveal within `150ms` or instantly. *Guardrail*: Never repeat a high-contrast solid-filled primary button on every row of a collection, and never animate hover-revealed row actions with staged or keyframe entrance effects.

## Peer Geometry Locking, Virtualization, and Reordering

- **When** peer cards or record blocks sit in the same row of a grid, clamp variable-length text fields to a fixed maximum line count and pin the action region to the bottom edge of the card so all peers in a row share an identical height and aligned bottom baseline.
- **When** a list or table can render more than `50` items, virtualize the collection (or apply `content-visibility: auto` / pagination) rather than mounting every DOM node at once. *Guardrail*: Never `.map()` unbounded arrays directly into the DOM without virtualization or pagination.
- **When** a list, table, or board supports drag-and-drop reordering or movement, provide a single-pointer alternative (such as move-up/move-down buttons or a move menu on each item) and a keyboard path that achieves the exact same result.

## Data Charts and Visual Encoding

- **When** rendering a plotted chart with coordinate axes, anchor bar and count y-axes at `0` using evenly spaced round tick intervals (integers for counts) whose top tick sits above the data maximum, and place horizontal unrotated x-axis labels on one uniform step interval spaced to fit the container width without colliding. *Guardrail*: Never omit the y-scale on a plotted chart, never start a bar or count axis above `0` or let the series touch or clip the top tick, never insert an irregular closing step on a time axis, and never rotate axis labels diagonally or vertically.
- **When** plotting a line series across discrete time periods or into future projections, connect measured data points with straight line segments so the curve never invents intermediate values between periods, and switch any projected or forecast segment after the current timestamp to a dashed stroke. *Guardrail*: Never apply spline or bezier smoothing across discrete period totals, and never draw forecasted values with the same solid stroke as recorded history.
- **When** encoding series colors and legends on a chart, assign the primary data hue to the main series under inspection while keeping comparison series in neutral or distinct semantic tones (reusing the same hue for the same entity across the screen), omit the legend when a single series is plotted, and render each multi-series legend swatch from the exact stroke, fill, or pattern of its plotted mark for series that have data on screen. *Guardrail*: Never render a legend for a single-series chart or for an empty series, never draw legend swatches with styling separate from the plotted mark, and never assign different hues to the same entity across sibling charts.
- **When** marking a threshold or an anomalous spike/step on a chart, draw a reference threshold as a `1px` dashed line labeled at its end and mark an event spike with a vertical leader line into a non-overlapping label row reserved above the plot only when annotations are present, laying out all chart labels after fonts load so no label or leader line collides with plotted marks or another label. *Guardrail*: Never reserve an empty annotation band above a chart that has no event annotations, and never allow axis ticks, threshold labels, or leader lines to cross through plotted series or other text.
