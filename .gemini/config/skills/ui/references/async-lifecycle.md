# Asynchronous Lifecycle and Data Mutations

Apply the rules below when the interface awaits asynchronous data, renders query-dependent collections, announces dynamic status updates, or performs data-mutating actions.

## Geometry Preservation, Live Announcements, and State Feedback

- **When** an interface region awaits asynchronous data (or loads images and media), render a skeleton placeholder matching the exact geometry of the populated content, set `aria-busy="true"` on the updating region, declare explicit `width` and `height` (or `aspect-ratio`) on every `<img>` (`loading="lazy"` below the fold, `fetchpriority="high"` on critical above-the-fold imagery), and handle slow or timed-out requests with an explicit status and retry/cancel action. *Guardrail*: Never replace a content region with a bare centered spinner that collapses container height and shifts surrounding layout when data arrives.
- **When** a data collection returns zero items, distinguish the cause: if the collection has never been populated, state what the view holds and why it is empty and provide one primary action to create the first item (when the user has permission); if the empty result comes from an active search query or filter, name the active query/filter and provide an immediate control to clear or reset it. *Guardrail*: Never render a dead-end empty message (`"No results"`, `"No data"`) with no way forward, and never place persistent feature instructions solely inside an empty state where they disappear as soon as the first item exists.
- **When** a fetch or mutation fails (or a surface is restricted by permissions), preserve all user-entered input, display a contextual error message in calm, plain language that states what failed and the exact next step to recover, and provide an immediate retry or recovery action; for `403` or read-only permission states, state why access is restricted and how to request permission. *Guardrail*: Never clear user input on a failed request, never use blame, humor, `"Oops!"`, `"Something went wrong"`, or exclamation marks `!` in error copy, and never expose raw HTTP status codes or stack traces as user-facing copy.
- **When** the user triggers a data-mutating action and the request is in flight, keep the button's original action label visible beside the progress indicator (or use parallel in-progress phrasing ending with `…` that resolves to the past-tense completion state), set `aria-disabled="true"` on the busy control, and ignore repeat activations in the handler until the request settles. *Guardrail*: Never replace a button's label with a bare spinner (which strips its accessible name while busy), and never set native `disabled` on a focused submit button mid-request (which drops keyboard focus to `<body>`).
- **When** announcing dynamic state changes not already communicated by moving focus or by a field's `aria-describedby`, render a stable empty live region in the DOM ahead of time using `role="status"` (`aria-live="polite"`) for non-urgent updates (toasts, save confirmations, updated result counts) and reserve `role="alert"` (`aria-live="assertive"`) exclusively for urgent untied errors; keep keyboard focus where the user is working rather than moving it to a toast, keep any toast carrying an action (`Undo`) or an error visible until explicitly dismissed, and give auto-dismissing status toasts at least `5 seconds` while pausing the timer on hover or focus. *Guardrail*: Never mount a `<div role="status">` conditionally at the same instant as its text (`{msg && <div role="status">{msg}</div>}`), never use `aria-live="assertive"` or `role="alert"` on success messages, and never place critical recovery actions solely inside a timed element that vanishes on its own.
