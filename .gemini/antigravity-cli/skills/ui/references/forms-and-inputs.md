# Forms, Inputs, and Validation

Apply the rules below when the interface includes forms, text inputs, selection controls, or user data submission flows.

## Labels, Input Configuration, and Target Geometry

- **When** rendering any form control (`<input>`, `<textarea>`, `<select>`, checkbox, radio), associate a persistent visible `<label for="...">` pointing at the control's `id` (or wrap `<label>` around both the control and text for checkboxes/radios so they share a single hit target with zero dead zone between them), mark required fields with native `required` plus a visible indicator explained once per form, and display known input constraints (such as character minimums or required formats) as persistent helper text linked via `aria-describedby` before the user types. *Guardrail*: Never use a `placeholder` as a substitute for a visible `<label>`, and never write instructions inside a `placeholder` (placeholders show only a realistic format example or end with `…` on search fields).
- **When** configuring input attributes inside a native `<form>`, provide a descriptive `name` and a valid `autocomplete` token (`name`, `given-name`, `family-name`, `email`, `tel`, `street-address`, `postal-code`, `country`, `cc-number`, `cc-exp`, `cc-csc`, `username`, `current-password`, `new-password`, `one-time-code`; set `autocomplete="off"` on non-auth business fields to prevent false password-manager prompts), pair `type` and `inputmode` to summon the matching mobile keyboard (`type="email"`, `type="url"`, `type="tel"`; `type="text" inputmode="numeric"` for OTP/PIN/card numbers to preserve text semantics without a number spinner; `type="text" inputmode="decimal"` for money/decimals; `type="number"` only for true numeric quantities), and set `spellcheck="false"`, `autocorrect="off"`, and `autocapitalize="off"` on emails, codes, usernames, and identifiers. *Guardrail*: Never block `paste` (`onPaste` + `preventDefault`) on any field including passwords and one-time codes, and never set `autoFocus` on mobile viewports.
- **When** sizing form inputs, match field width to expected value length (sizing short-value fields like postal codes, OTP codes, dates, and quantities narrower than long-value fields) or lock inputs to the form's shared column grid. *Guardrail*: Never stretch short-value inputs across the full width of a wide desktop viewport.

## Submit-Time Validation and Unsaved-Change Protection

- **When** validating user input, keep the submit button enabled, accept free text, and `trim()` leading/trailing whitespace (added by autofill or text expansion) before validating; on submit, if validation fails, block the request, mark each failing field `aria-invalid="true"` (removing it once fixed), render a positive instruction stating how to satisfy the requirement beside the field with an icon or text cue linked via `aria-describedby`, and move focus to the first invalid field. *Guardrail*: Never disable the submit button (`disabled={!isValid}`) to gate validation before the user submits, never block typing or filter characters per keystroke while the user types, and never signal an invalid field with a red border alone.
- **When** a form holds unsaved user edits (`dirty state`), warn before browser tab close or route navigation (`beforeunload` and router navigation guards), and ensure controlled inputs (`value` paired with `onChange`, or `defaultValue` for uncontrolled inputs), re-renders, and SSR hydration never reset typed characters or steal focus from the active field.
