# UI Architecture and Interface Review

## Precedence

1. **Unconditional requirements**: Accessibility, WCAG 2.2 AA contrast, keyboard and `:focus-visible` reachability, narrow-viewport and text-zoom reflow, and state-completeness thresholds (*Step 4* and *Technical Contracts*) apply to every run.
2. **Existing project preservation**: Preserve a project's deliberate density, styling conventions, typeface, brand voice, and factual copy unless asked to change them.
3. **Starting-point defaults**: Starting-point spacing, scale ratios, and motion values apply where the project or brief has no established system.

## Execution Workflow

Execute the following 4 steps in order:

1. **Establish run mode and active references**: Fix whether the run builds/modifies UI or reviews UI read-only, and apply *Precedence* above.
   - **When** modifying an existing codebase or reviewing an interface or diff, read `references/codebase-and-review.md` to inventory project conventions, expand diff blast radius, and format the review report.
   - **When** creating a new color palette, wide-gamut gradient, dark mode, or `prefers-contrast` theme, read `references/color-and-themes.md` to construct OKLCH ramps, sRGB fallbacks, and theme overrides.
   - **When** the interface renders repeated records, quantitative metrics/deltas, or charts, read `references/data-collections.md` to allocate primary versus detail attributes, reconcile numbers, and encode chart series.
   - **When** the interface includes form fields, selection controls, or submission flows, read `references/forms-and-inputs.md` to bind labels, mobile keyboards, autocomplete, submit-time validation, and dirty-state guards.
   - **When** the interface animates state transitions, handles drag/swipe gestures, or considers an overlay above the canvas, read `references/motion-and-overlays.md` to choose inline versus overlay disclosure and configure interruptible motion, focus containment, and gesture cleanup.
   - **When** the interface awaits asynchronous data, mutates server state, or announces dynamic updates, read `references/async-lifecycle.md` to preserve layout geometry across loading, empty, error, busy, and live-region states.
   - **When** the interface supports multiple locales, formats locale-dependent dates/numbers/lists, or renders bidirectional (LTR/RTL) content, read `references/i18n.md` to apply logical CSS properties, directional icon rules, and `Intl` message formatting.
   *Completion criterion*: Run mode (build/modify vs read-only review) is stated, every matching `references/*.md` file is read, and existing project conventions (plus full diff hunks and consumer blast radius in a change review) are inventoried with `file:line` citations.

2. **Emit individual causal rulings before constructing output**: Before emitting any code or review output, walk every applicable `**When**` rule in this skill and opened `references/*.md` files whose decision can vary across individual items in scope. For each such rule—at every nesting level of the interface—identify every concrete item governed by its cause (citing where it sits in the work), state the rule's causal ruling on each item individually while holding all other items fixed (never grouping items into one shared ruling), and emit zero deliverables until every applicable item has an explicit ruling.
   *Completion criterion*: Every concrete item at every nesting level governed by an item-varying `**When**` rule has an emitted individual ruling citing where it sits, zero items share a grouped ruling, and zero code mutations or review outputs have been emitted yet.

3. **Construct interface code or evaluate review scope strictly from rulings and contracts**:
   - **When** building or modifying UI, write markup, styles, and state handlers strictly from Step 2's individual rulings and all applicable contracts below and in opened `references/*.md` files, choosing the earliest tier that resolves each need: *(1) Delete redundant elements $\rightarrow$ (2) Reuse existing project components, macros, and tokens $\rightarrow$ (3) Correct the token or CSS value $\rightarrow$ (4) Build or extend a reusable unit per Accessibility Mechanics and Landmarks*.
   - **When** reviewing UI, verify every inspected file and expanded consumer against Step 2's rulings and all applicable contracts without modifying workspace files.
   *Completion criterion*: Every Step 2 ruling maps 1-to-1 to the constructed code or review findings, every applicable contract holds across all states and viewports, and zero workspace files are modified in a review run.

4. **Verify runtime or computed behavior by impact order and deliver**: Verify layout reflow (`320px` width and `200%` text zoom), WCAG contrast pairs, keyboard tab/focus order, and lifecycle states in the live browser or test runner when available, or by static computed analysis when bounded, resolving defects in strict impact order (mapping to `HIGH`/`MEDIUM`/`LOW` in review runs per `references/codebase-and-review.md`): *(1) Task blockers, data-loss risks, missing accessible names/keyboard paths/focus rings, clipping or overlap at `320px` width or `200%` zoom, failing WCAG contrast pairs, or state carried by color/motion alone $\rightarrow$ (2) Missing lifecycle states (loading, empty, error, busy, disabled, permission) $\rightarrow$ (3) Hierarchy, layout, terminology, URL state, or design-token drift $\rightarrow$ (4) Surface, radius, or motion polish*.
   *Completion criterion*: Delivered UI code satisfies every applicable rule with zero arbitrary spacing or color literals outside the system scale and zero unresolved Tier-1 defects (or delivered review report matches the anchor in `references/codebase-and-review.md`), and every check that could not be verified at runtime is explicitly named together with the concrete risk it leaves.

## Core Architecture

### Minimalism and Progressive Disclosure

- **When** deciding what to show on initial render in the active scope and recursively inside every sub-scope opened from it, assign each unit to one of three tiers: (1) show it in full immediately when every visit needs it, the interface intentionally directs attention to it, or it is placed for deliberate aesthetics; (2) hide its body by default behind a clearly visible labeled trigger when it is used often but not always needed; (3) hide its body by default behind a minimal-footprint trigger carrying just enough cue for users to guess where it sits when it is rarely needed.

### Visual Signal Hierarchy

- **When** displaying multiple data attributes in the same container, place identifying content and the primary value near the top and leading edge and scale each element's glyph size, stroke weight, and lightness contrast in proportion to the order the user needs it to identify the record and make a decision, so visual order matches DOM order and blurring lower-tier details still leaves the primary element, secondary element, and major groups identifiable at a glance. *Guardrail*: Never assign a static label a font weight or contrast equal to or stronger than the dynamic value it describes, and never move content out of DOM sequence with CSS `order`, `row-reverse`, or grid placement.
- **When** deciding whether to display a static label beside a data value, omit the static label if the value's format, unit, or placement uniquely identifies its meaning while sibling values in that region are held fixed; keep the static label and step its size and contrast below its paired value when sibling values share a format that prevents telling them apart by value alone.
- **When** evaluating any non-content visual mark in a container, include it only if removing it while holding spacing fixed loses structural information about the content that spacing alone cannot express.

### Spatial Boundaries and Surfaces

- **When** arranging elements across hierarchy levels, take all `padding` and `gap` values from a fixed system spacing scale and increase spacing strictly from inner to outer nesting levels ($d_{\text{internal}} < d_{\text{between-groups}} \le p_{\text{container}}$), with more space above a section heading than between that heading and the content below it, letting parent containers own spacing between children. *Guardrail*: Never repeat a uniform spacing value across different structural levels, and never hardcode outer margins directly inside a reusable child component.
- **When** separating content regions, establish boundaries with stepped negative space first, a borderless background surface shift (`background-color` contrast with `border: none`) second, or a single shared `1px` hairline divider between adjacent items last—reserving perimeter `1px` borders exclusively for discrete interactive controls (form inputs, outlined buttons, selected states) and floating overlays (paired with `border: 1px solid transparent` on shadowed overlays for `forced-colors` mode), and reserving a `2px–3px` `border-inline-start` stroke exclusively for unframed, unrounded open edges that mark a `<blockquote>`, a nested thread/tree indentation rail, or the single active item (`aria-current`) along a vertical navigation rail. *Guardrail*: Never place bordered content boxes (cards, panels, callouts, or list rows) beside or inside another bordered box so that two borders run in parallel, never add a `border-left` / `border-inline-start` thicker than `1px` on cards, callouts, alerts, or list items, and never pair a separator line with a large gap that already separates the groups.
- **When** assigning `border-radius` across surfaces and controls, take radius values from a fixed system token scale stepped down by surface hierarchy (larger tokens on outer panels and cards, medium tokens on inputs, buttons, and callouts, and smaller tokens on compact badges).

### Action and Control Hierarchy

- **When** binding interactive elements and widget surfaces, use semantic HTML primitives whose visual rendering is fully governed by project CSS (`<button>` for actions, `<a href>` for navigation that changes the URL so Cmd/Ctrl/middle-click works, `<label>` and `<form>` for inputs), build any control with a popup or custom surface with project styles, ARIA roles, and keyboard handlers rather than browser-rendered widget chrome, give every interactive element a visual cue distinct from static prose (background fill, border, underline, or dedicated toolbar zone), and apply `pointer-events: none` (plus `aria-hidden="true"` on DOM elements) to decorative glow/scrim overlays so they never block controls beneath them. *Guardrail*: Never use native browser-chrome widgets or OS dialogs whose visual surface, popup, or sub-controls cannot be styled through project tokens (`<select>`, `<option>`, `<input type="date" | "time" | "datetime-local" | "month" | "week" | "color">`, unstripped `<input type="checkbox" | "radio" | "range">` without `appearance: none`, native `title` tooltips, or `window.alert` / `confirm` / `prompt`; see `references/forms-and-inputs.md` for numeric inputs and steppers), never attach `onClick` to a `<div>` or `<span>`, never style a static badge identically to adjacent buttons, and never put `aria-hidden="true"` on a focusable element or its ancestor.
- **When** multiple actions appear in the same decision scope, assign the high-contrast solid fill to at most one primary action (putting the accent color on the background, not the label) and demote secondary actions to outlined, subtle, or text treatments. *Guardrail*: Never place two high-contrast solid-filled peer buttons side by side in the same control group, and never use accent-colored text on a neutral button to signal primary emphasis.
- **When** designing a data-mutating or destructive action, choose between immediate execution with `Undo` and pre-action confirmation based on reversibility and blast radius: if the action can be reversed and is performed routinely, execute it immediately with an `Undo` toast (see `references/async-lifecycle.md` for toast persistence); if the action cannot be reversed, affects other users, or destroys multiple items at once, style its trigger in the primary view with low-contrast treatment and require a confirmation dialog (see `references/motion-and-overlays.md` for dialog focus) whose title and confirm button both state the exact verb and target object and whose body states what is permanently lost (including item counts and affected users where applicable; for high-impact shared containers, require typing the object's name before enabling confirmation). *Guardrail*: Never title a confirmation dialog `"Are you sure?"`, and never execute an irreversible destructive action immediately without confirmation.

## Technical Contracts

### Contrast and Semantic Color Tokens

- **When** referencing colors inside components, use *Semantics* tokens named by role (`--color-bg-surface`, `--color-text-secondary`, `--color-border-subtle`, `--color-accent-solid`) rather than *Primitives* named by hue and step (`--blue-600`) or raw color literals, and assign each hue (treating anything within `15deg` of OKLCH hue as the same color) one meaning across the interface. *Guardrail*: Never write raw color literals (hex, `rgb()`, `oklch()`) or primitive tokens inside components where tokens exist, never borrow a token from another role because its value matches today, and never define both `--color-primary` and `--color-text-primary` (use `accent` for the brand color and reserve `primary` for hierarchy rank).
- **When** rendering text, icons, focus indicators, or control boundaries against any background (including translucent surfaces, gradients, images, and hover/selected states), ensure the rendered foreground-against-background pair meets WCAG 2.2 AA minimum contrast—`4.5:1` for normal text (`< 24px` regular or `< 18.67px` bold) and `3:1` for large text (`>= 24px` or `>= 18.67px` bold), UI component boundaries, `:focus-visible` rings, and meaningful icons—adjusting perceived lightness while holding hue constant and remeasuring when color remediation is requested, and always pairing status or meaning carried by color with a second visual cue (icon, text label, or underline). *Guardrail*: Never let color be the sole carrier of state or meaning, never fix contrast by shifting hue instead of lightness, never place text on an unmeasured translucent/image background without a scrim or worst-region verification, and never put white text on a mid-ramp `500` fill that fails `4.5:1` (use step `600` or Radix step `9` for solid fills).

### Accessibility Mechanics and Landmarks

- **When** structuring page landmarks and component encapsulation, render feature views from the project's reusable components, macros, or partials when the stack provides them (confining raw HTML interactive tags to their internal definitions) or write semantic HTML directly with shared CSS classes and tokens in raw-HTML stacks, and wrap page structure in `<header>`, `<nav>`, `<main id="main">`, `<aside>`, and `<footer>` landmarks (with distinguishing `aria-label`s when multiple landmarks share a tag), sequential `<h1>–<h6>` headings, and a visually hidden `.sr-only` `"Skip to content"` link (`1px` dimensions with `clip-path: inset(50%)` and `white-space: nowrap`) as the first focusable element when chrome precedes `<main>`. *Guardrail*: Never write raw HTML interactive controls directly in feature views when the project provides a component or macro for them, and never use `0px` dimensions on `.sr-only`.
- **When** rendering `<img>` elements, set `alt` on every image: `alt=""` for decorative images, content meaning for informative images, and action/destination for functional images inside controls or links.
- **When** sizing touch/pointer targets and spacing adjacent controls, provide a hit area of at least `24×24` CSS pixels (targeting `44×44px` on touch and `40×40px` on desktop; when the visible glyph is smaller, expand the hit target with a centered `::after` pseudo-element on the `<button>` or wrapper), set `touch-action: manipulation` on interactive controls, and separate adjacent bordered/filled controls by at least `12px` and visible glyphs of adjacent borderless text/icon controls by at least `24px`. *Guardrail*: Never place a hit-area pseudo-element directly on `<input>`, and never allow expanded hit areas of adjacent controls to overlap.
- **When** implementing keyboard navigation and focus indicators, provide a keyboard path for every pointer interaction matching the visual/DOM reading order (`tabindex="0"` for natural tab order, `tabindex="-1"` for programmatic focus, `roving tabindex` on composite widgets like tabs, menus, toolbars, and radio groups so the widget takes one Tab stop and arrow keys move inside it, or `aria-activedescendant` when focus stays in a combobox input) and render a `:focus-visible` ring with at least `3:1` contrast against every adjacent surface it crosses (preferring the browser ring with `outline-offset: 2px` or a verified `2px solid` focus token, and `:focus-within` on compound input wrappers). *Guardrail*: Never use a positive `tabindex` (`1`, `2`...), and never set `outline: none` or `outline-none` without a verified `:focus-visible` replacement.
- **When** a control is unavailable, use native `disabled` (or `aria-disabled="true"` with pointer/keyboard activation blocked in code when keeping the control discoverable in the tab order is intentional) and state why the control is unavailable and how to unlock it in visible text beside the control (for pre-submit forms see `references/forms-and-inputs.md`; for in-flight requests see `references/async-lifecycle.md`). *Guardrail*: Never attach a tooltip to a natively `disabled` control, and never set both `disabled` and `aria-disabled` on the same element.

### Viewport, Grid/Flex, and State

- **When** placing chrome, sections, or stacked content blocks within the same scroll canvas, lock their start and end edges onto shared outer inline margins and inner alignment axes so same-side edges form continuous vertical and horizontal lines, repeating one project indent step per level of nesting. *Guardrail*: Never put canvas header chrome and body sections on mismatched outer inline insets, and never center-align text blocks of two or more lines or vertically scanned data collections.
- **When** sizing section and card heights, size containers to their content (`height: auto`), applying explicit viewport-relative height only on split/hero sections where media or focal display typography anchors the opposite edge and content still expands without clipping at `200%` text zoom. *Guardrail*: Never stretch a card or section height over an empty blank band (`min-height: 100dvh` on short content), and never invent decorative filler elements to plug empty space.
- **When** displaying continuous prose on a wide viewport, cap the prose measure at `60–75ch` so the start of a line and its end sit within a single horizontal eye sweep, allocating remaining viewport width to multi-column layout or surrounding whitespace.
- **When** sizing CSS Grid/Flex tracks, full-viewport panes, and text containers, set flexible grid tracks to `minmax(0, 1fr)`, flex children to `min-width: 0`, full-width containers to `width: 100%`, document-scrolling full-viewport shells to `min-height: 100dvh` (using `height: 100dvh` on full-height panes whose inner container owns `overflow-y: auto`), and text containers to `min-height` (or `max-height` paired with `overflow-y: auto`), adapting reusable components to their parent slot using `@container` queries on a container with a definite width rather than viewport `@media` queries. *Guardrail*: Never use `100vw`, never use `100vh` on full-height mobile panes, never put a fixed `height` on a box holding text, never apply `container-type: inline-size` to a shrink-to-fit element without a definite width, and never set `maximum-scale=1` or `user-scalable=no` in `<meta name="viewport">`.
- **When** positioning controls near viewport edges or pinning (`sticky` / `fixed`) chrome above scrolling content, inset controls from viewport edges by at least `16px` plus `env(safe-area-inset-*)` (declaring `viewport-fit=cover` in `<meta name="viewport">`), give pinned chrome an opaque background surface or a dedicated non-overlapping layout track, set `scroll-padding-block-start` / `scroll-padding-block-end` on the scroll container to match the pinned chrome height, and set `scroll-margin-block-start` on anchored headings. *Guardrail*: Never float transparent or unbacked text controls directly over scrolling text or imagery, and never park a primary or critical action where resizing to `320px` width, scaling text to `200%`, or opening the mobile on-screen keyboard clips it.
- **When** variable-length content is truncated with single-line ellipsis or `-webkit-line-clamp` or sits past a scroll edge or behind a disclosure, provide a keyboard- and touch-reachable path to the full text (an expand control, detail view, or focus-reachable tooltip) and signal off-screen scrollable content by letting the next item peek `16–32px` past the scroll edge or rendering a disclosure control that states the hidden item count.
- **When** an interface holds stateful navigation that determines the active view (including filters, search queries, sort order, active tabs, pagination, or expanded detail panels), synchronize that state into URL query parameters so reloading, navigating back/forward, or sharing the link restores the exact view.

### Typography, Icons, and Copy

- **When** selecting font families and loading faces, use at most three font families (defaulting to one sans-serif family on *Operate* surfaces), load every declared `@font-face` weight and style so the browser never synthesizes a missing face, and use standard CSS typographic properties (`font-weight`, `font-variant-numeric`, `slashed-zero`, `font-variant-caps`, `font-variant-position`) instead of raw OpenType tags. *Guardrail*: Never set `font-synthesis: none` globally on body text without verifying the fallback stack, and never use `font-variation-settings` (`"wght"`) or `font-feature-settings` (`"tnum"`, `"zero"`) where a standard CSS property exists.
- **When** defining font sizes and weights across the hierarchy, declare `font-size` in `rem` on a semantic role scale (`1.125–1.2` ratio on *Operate/Read* surfaces, starting long-form body text at `1rem`/`16px`, menus and desktop inputs at `0.875rem`/`14px` while keeping editable text inputs `>= 1rem`/`16px` on mobile viewports so iOS Safari never force-zooms on focus, and captions at `0.8125rem`/`13px`, rarely below `12px`), map `h1–h6` to descending scale steps so a subordinate heading never overpowers its parent, and use weight `400` or heavier on all text below `18px` (reserving weights `100–300` for `28px` and up).
- **When** setting `line-height` and `letter-spacing`, declare `line-height` as a unitless multiplier (`1.1` for display text, `1.2–1.3` for headings, `1.5–1.6` for body copy, and at least `1.4` on any description or card text that can wrap to three or more lines) and declare `letter-spacing` in `em` (`-0.01em` to `-0.02em` on headings at `24px` and up, `0.05em` on uppercase labels at `14px` or smaller, and `0` on body copy). *Guardrail*: Never declare `line-height` or `letter-spacing` in fixed `px`, and never set `font-kerning: none`.
- **When** controlling text alignment, wrapping, and selection, set `text-align: start` on interface text, apply `text-wrap: balance` to headings and short descriptions of six lines or fewer, apply `text-wrap: pretty` to paragraphs, set `overflow-wrap: break-word` where long words, URLs, or identifiers can overflow, set `white-space: nowrap` on badges and compact labels where wrapping breaks visual integrity, store copy in natural case using CSS `text-transform` for visual casing, keep straight quotes inside `<code>`/`<pre>` blocks, and keep text selectable by default (see `references/motion-and-overlays.md` for active drag surfaces). *Guardrail*: Never use `text-align: justify` in application UI, never apply `text-wrap: balance` to multi-sentence paragraphs, never convert straight quotes inside `<code>` or `<pre>` blocks into curly quotes, and never set `user-select: none` on static or standard interactive content.
- **When** pairing icons with text or rendering standalone icons, draw every icon as an SVG from a single icon library per surface, size inline icons at `1em–1.25em` of the adjacent text, match rendered SVG stroke width to adjacent text weight (`1.5px` for 400 regular, `2px` for 500–600 medium/semibold, `2.5px` for 700 bold, using `vector-effect: non-scaling-stroke` or absolute stroke sizing), and color icons via `currentColor` driven by CSS state (`outline` variant for default state, `fill` variant for active/selected state). *Guardrail*: Never use Unicode glyphs or emoji in place of a drawn SVG icon system, never mix icon libraries on the same surface, never use filled icons for both default and active states, and never leave hardcoded `fill="#..."` or `stroke="#..."` values inside an icon SVG.
- **When** writing interface copy, labels, and links, apply one consistent capitalization policy per element type, assign one noun per domain object and one verb per action across the entire product, write button labels as concise action verbs when the enclosing card or row already identifies the target object (naming both action verb and target object when context is ambiguous and inside every icon-only or repeated control's `aria-label`), write link text that names its destination when read out of context (distinguishing multiple links on the same page by naming each target), and phrase toggle/switch labels to describe what happens when the state is ON. *Guardrail*: Never use generic confirmation labels (`OK`, `Yes`, `No`), never name an icon-only control after its glyph (`Trash icon`, `Close icon`, `X`) or omit visible label text from its `aria-label`, never write `Click here` or duplicate identical bare `Learn more` links on one page, and never phrase a toggle label as a negative (`Don't...`, `Disable...`, `Hide...`).
- **When** composing the opening viewport and narrative sections of a *Persuade/Experience* surface, state what the subject is and expose the primary next action on the first screen with the display `<h1>` holding display scale above body text, and give each narrative section one distinct claim backed by verifiable proof from the brief or product itself, grounding every statement in concrete attributes of the subject that become false if a competitor's name is substituted. *Guardrail*: Never shrink a display `<h1>` to body size, never leave the first viewport without a plain statement of what the subject offers, never add filler sections carrying no distinct claim, never write interchangeable category slogans that remain true for a competitor, and never fabricate external facts, endorsements, certifications, or metrics not supplied in the brief.
