# UI Architecture and Interface Review

Build, modify, or review user interfaces so that visual reading order, spatial grouping, typography scales, semantic color palettes, accessibility, and interactive feedback directly match business priority and actual data state. Accessibility, contrast, keyboard/focus, text-zoom/reflow (`320px` and `200%`), and state-completeness thresholds in this skill are unconditional requirements; starting-point spacing, scale ratios, shadow recipes, and motion values apply where the project or brief has no established system—preserve a project's deliberate density, styling conventions, typeface, brand voice, and factual copy unless asked to change them.

## Execution Workflow

Execute the following 4 steps in order:

1. **Establish surface mode, information hierarchy, and viewport capacity**: Identify the surface mode from the user's goal (*Operate/Read* — where the user completes a task or reads for comprehension: prioritize scanability, information density, familiar standard controls, a fixed `rem` type scale at a `1.125–1.2` ratio, and loading straight into the task without page-load choreography $\neq$ *Persuade/Experience* — where design is the product or showcase: prioritize subject-grounded visual expression and narrative composition), then classify all data attributes and actions by *Visual Signal Hierarchy*, *Typography and Interface Copy*, and *Alignment Axes and Viewport Capacity*. **When** the interface renders repeated records or quantitative values compared across items, time, or totals, read `references/data-collections.md` to structure record density, numeric reconciliation, and visual data encoding. *Completion criterion*: Every display region has one clear primary visual anchor, visual order matches DOM order, redundant static labels are removed, and the minimum total width of horizontal sibling elements fits inside the container down to a `320px` viewport and at `200%` text zoom without horizontal overflow.
2. **Establish spatial geometry, color tokens, and interaction hierarchy**: Shape grouping structure, border radii, surface elevation, color tokens, and control prominence according to *Spatial Grouping and Container Surfaces*, *Color Systems and Visual Contrast*, and *Interactive Control Weight and Accessibility*. **When** the interface contains forms, text inputs, or user submission flows, read `references/forms-and-inputs.md` to configure programmatic labels, keyboard types, autocomplete, submit-time validation, and unsaved-change protection. **When** the interface includes state transitions, pointer/gesture feedback, or overlays (modals, drawers, popovers, menus, tooltips), read `references/motion-and-overlays.md` to configure interruptible transitions, scroll containment, focus trapping, and interrupted-gesture cleanup. *Completion criterion*: Spacing strictly increases from inner to outer nesting levels, peer elements share alignment edges, each decision scope has at most one primary filled action, and every pointer interaction path is completable by keyboard with a visible `:focus-visible` indicator.
3. **Lock geometry against data, state, and locale variation**: Lock containers against variable text lengths and synchronize navigation state according to *Alignment Axes and Viewport Capacity*. **When** the interface loads asynchronous data, announces dynamic updates, or mutates data, read `references/async-lifecycle.md` to configure geometry-preserving skeletons, screen-reader live regions (`role="status"` / `role="alert"`), and explicit views for loading, empty, error, and pending-mutation states. **When** the interface supports internationalization, renders bidirectional (LTR/RTL) user data, or modifies/reviews an existing codebase, read `references/i18n-and-review.md` to apply logical CSS properties, `Intl` formatting, codebase convention inventory, and blast-radius review expansion. *Completion criterion*: Every region holding variable-length text or asynchronous data preserves the geometry of surrounding blocks, reflects stateful navigation in the URL, and renders explicit UI for every lifecycle state.
4. **Cross-check by priority order and deliver output**: Verify every component, state, and viewport in scope against all applicable rules in this document and opened reference files, fixing defects in strict impact order: *(1) Task blockers, data-loss risks, missing accessible names/focus rings/keyboard paths, clipping or overlap at `320px`/`200%` zoom, or failing contrast pairs $\rightarrow$ (2) Missing lifecycle states (loading, empty, error, disabled, permission) $\rightarrow$ (3) Hierarchy, layout, terminology, or design-token drift $\rightarrow$ (4) Surface, radius, or motion polish*; when choosing a fix, take the earliest tier that resolves the cause: *Delete redundant elements $\rightarrow$ Reuse existing project components, macros, and tokens $\rightarrow$ Correct the value $\rightarrow$ Build or extend a project component/macro (or shared-class semantic HTML in raw-HTML stacks) wrapping semantic HTML primitives*. *Completion criterion*: Delivered interface code or review output satisfies every applicable rule across all inspected surfaces with zero arbitrary spacing or color literals left outside the system scale, and explicitly names any check that could not be verified at runtime along with the risk it leaves.

## Visual Signal Hierarchy

The eye scans an interface in descending order of visual signal contrast (driven by glyph size, stroke weight, and lightness contrast against the background).

- **When** displaying multiple data attributes in the same container, place identifying content and the primary value near the top and leading edge, and scale each element's visual contrast in proportion to the order the user needs it to identify the record and make a decision, so that visual order matches DOM order and blurring lower-tier details still leaves the primary element, secondary element, and major groups identifiable at a glance. *Guardrail*: Never assign a static label a font weight or contrast equal to or stronger than the dynamic data value it describes, and never move content out of source DOM sequence with CSS `order`, `row-reverse`, or grid placement.
- **When** a value's format, accompanying unit, or placement already uniquely identifies its meaning in context, render the value directly and omit the static label.
- **When** multiple values in the same region share a format such that users cannot tell them apart by value alone, keep the static labels but step their size and contrast below their paired values.
- **When** considering structural visual devices such as numbering, dividers, or badges, include a device only when it encodes actual structural information about the content that spacing alone cannot express (such as using `01 / 02 / 03` markers only when items represent a sequential process or timeline). *Guardrail*: Never use Unicode glyphs or emoji in place of a drawn SVG icon system.

## Typography and Interface Copy

Typography sets the information hierarchy and reading rhythm, while interface copy tells users what a control does and how to move forward.

- **When** selecting font families and loading font faces, use at most three font families (defaulting to one sans-serif family on Operate surfaces), load every `@font-face` weight and style the design declares so the browser never synthesizes a missing face, and use standard CSS typographic properties (`font-weight`, `font-variant-numeric: tabular-nums`, `slashed-zero`, `font-variant-caps`, `font-variant-position`) instead of raw OpenType tags. *Guardrail*: Never set `font-synthesis: none` globally on body text without verifying the fallback stack, and never use `font-variation-settings` (`"wght"`) or `font-feature-settings` (`"tnum"`, `"zero"`) where a standard CSS property exists.
- **When** defining font sizes and weights across the hierarchy, declare `font-size` in `rem` on a semantic role scale (starting long-form body text at `1rem`/`16px`, inputs and menus at `0.875rem`/`14px`, and captions at `0.8125rem`/`13px`, rarely below `12px`), map heading levels `h1–h6` to descending steps of the scale so a subordinate heading never overpowers its parent, and use font weight `400` or heavier on all text below `18px` (reserving weights `100–300` for `28px` and up).
- **When** sizing editable text inputs on mobile viewports, keep the input's computed `font-size` at `16px` or larger so iOS Safari never force-zooms the viewport on focus.
- **When** setting line-height (`leading`) and letter-spacing (`tracking`), declare `line-height` as a unitless multiplier (`1.1` for display text, `1.2–1.3` for headings, `1.5–1.6` for body copy, and at least `1.4` on any description or card text that can wrap to three or more lines), and declare `letter-spacing` in `em` (`-0.01em` to `-0.02em` on headings at `24px` and up, `0.05em` on uppercase labels at `14px` or smaller, and `0` on body copy). *Guardrail*: Never declare `line-height` or `letter-spacing` in fixed `px`, and never set `font-kerning: none`.
- **When** controlling text wrapping, alignment, punctuation, and selection, set `text-align: start` on interface text, apply `text-wrap: balance` to headings and short descriptions of six lines or fewer, apply `text-wrap: pretty` to paragraphs, set `overflow-wrap: break-word` where long words, URLs, or identifiers could overflow their container, set `white-space: nowrap` on badges and compact labels where a line break breaks visual integrity, store copy in natural case using CSS `text-transform` for visual casing, render typographic punctuation (`…`, en dash `–` for ranges, em dash `—`, and curly quotes in prose while keeping straight quotes in code), and keep text selectable by default. *Guardrail*: Never use `text-align: justify` in application UI, never use `text-wrap: balance` on multi-sentence paragraphs, never output raw `...` or `--` in rendered prose, never convert straight quotes inside `<code>` or `<pre>` blocks into curly quotes, and never apply `user-select: none` outside draggable or gesture-driven surfaces where accidental selection interferes.
- **When** writing interface copy, labels, and links, address the reader directly in the second person (`"you"`), apply one consistent capitalization policy per element type (defaulting to sentence case), assign one noun per domain object and one verb per action across the entire product, start every button label (and every icon-only button's accessible name) with a verb naming the action and target object, write link text that names its destination when read out of context (distinguishing multiple links on the same page by naming each target), and phrase toggle/switch labels to describe what happens when the state is ON. *Guardrail*: Never use generic confirmation labels (`OK`, `Yes`, `No`), never name an icon-only control after its graphic glyph (`Trash icon`, `Close icon`, `X`) or omit visible label text from its `aria-label`, never write `Click here` or duplicate identical bare `Learn more` links on one page, and never phrase a toggle label as a negative (`Don't...`, `Disable...`, `Hide...`).
- **When** composing the opening viewport of a *Persuade/Experience* surface, state what the subject is and expose the primary next action on the first screen, authoring the display `<h1>` as a concise title (`≤ 32ch` / 4–6 words so it holds display scale within two lines down to a `320px` viewport) and placing sentence-length explanation in a supporting line directly beneath it. *Guardrail*: Never let a display `<h1>` wrap past two lines or shrink its font size to body scale to force a long sentence onto two lines, and never leave the first viewport without a plain statement of what the subject offers.
- **When** structuring sections and copy on a *Persuade/Experience* surface, give each narrative section one distinct claim backed by verifiable proof from the brief or product itself, and ground every statement in concrete attributes of the subject that would become false if a competitor's name were substituted. *Guardrail*: Never add filler sections that carry no distinct claim, never write interchangeable category slogans that remain true for a competitor, and never fabricate external facts, endorsements, certifications, or metrics not supplied in the brief.

## Spatial Grouping and Container Surfaces

Related items are perceived as a group when the space between them is smaller than the space separating them from surrounding groups.

- **When** arranging elements across hierarchy levels, take all padding and gap values from a fixed system spacing scale and increase spacing strictly from inner to outer nesting levels ($d_{\text{internal}} < d_{\text{between-groups}} \le p_{\text{container}}$), with more space above a section heading than between that heading and the content below it. *Guardrail*: Never repeat a uniform spacing value across different structural levels, and never hardcode outer margins directly inside a reusable child component.
- **When** separating content sections, cards, callouts, or record items, establish boundaries with stepped negative space first, a borderless background surface shift (`background-color` contrast with `border: none`) second, or a single shared `1px` hairline divider between adjacent items last—reserving perimeter `1px` borders exclusively for discrete interactive controls (form inputs, outlined buttons, selected states) and floating overlays (paired with `border: 1px solid transparent` on shadowed overlays for `forced-colors` mode), and reserving a `2px–3px` `border-inline-start` stroke exclusively for unframed, unrounded open edges that mark a `<blockquote>`, a nested thread/tree indentation rail, or the single active item (`aria-current`) along a vertical navigation rail. *Guardrail*: Never place bordered content boxes (cards, panels, callouts, or list rows) beside or inside another bordered box so that two borders run in parallel, never add a `border-left` / `border-inline-start` thicker than `1px` on cards, callouts, alerts, or list items, and never pair a separator line with a large gap that already separates the groups.
- **When** assigning `border-radius` across surfaces and controls, take radius values from a fixed system token scale stepped down by surface hierarchy (larger tokens on outer panels and cards, medium tokens on inputs, buttons, and callouts, and smaller tokens on compact badges); **when** a rounded child surface sits flush inside a rounded parent's corner across a uniform tight inset of `8px` or less (such as a pill inside a segmented control track or a media thumbnail inset inside a card edge), set the outer radius equal to the inner radius plus the inset ($R_{\text{outer}} = R_{\text{inner}} + p$). *Guardrail*: Never compute outer radii by summing padding past `8px` or adding border width ($R_{\text{inner}} + p + b$), and never give a parent and a corner-flush child the same `border-radius` when their inset is `8px` or less.
- **When** rendering content photographs or raster media (excluding transparent logos and illustrations), apply a `1px` inset outline in pure black or white (`outline: 1px solid oklch(0 0 0 / 0.1); outline-offset: -1px` in light mode and `oklch(1 0 0 / 0.1)` in dark mode) so the image edge stays crisp without altering layout box dimensions. *Guardrail*: Never outline content images with a tinted neutral, palette near-black (`outline-slate-*`, `#111827`), or accent color.
- **When** pairing icons with text or rendering standalone icons, use a single icon library per surface, size inline icons at `1em–1.25em` of the adjacent text, match rendered SVG stroke width to adjacent text weight (`1.5px` for 400 regular, `2px` for 500–600 medium/semibold, `2.5px` for 700 bold, using `vector-effect: non-scaling-stroke` or absolute stroke sizing), and color icons via `currentColor` driven by CSS state (`outline` variant for default state, `fill` variant for active/selected state). *Guardrail*: Never mix icon libraries on the same surface, never use filled icons for both default and active states, and never leave hardcoded `fill="#..."` or `stroke="#..."` values inside an icon SVG.

## Alignment Axes and Viewport Capacity

Every misaligned leading or trailing edge forces the eye to re-anchor, and whenever the minimum width of horizontal siblings exceeds the container, the layout clips or breaks across lines.

- **When** placing chrome, sections, stacked content blocks, or form fields within the same scroll canvas, lock their start and end edges onto shared outer inline margins and inner alignment axes so same-side edges form continuous vertical and horizontal lines, repeating one project indent step per level of nesting. *Guardrail*: Never put canvas header chrome and body sections on mismatched outer inline insets, never center-align text blocks of two or more lines or vertically scanned data collections, and never let stacked text inputs vary in width based on their label lengths.
- **When** sizing section and card heights, size containers to their content (or pair an intentional open rest with the section's media or focal typography across the opposite edge) so no blank vertical band remains inside a card or section. *Guardrail*: Never stretch a card or section height over an empty blank band (`min-height: 100dvh` on short content), and never invent decorative filler elements to plug empty space.
- **When** displaying continuous prose or a single-column group of form controls on a wide viewport, cap the prose measure at `60–75` characters per line (`60–75ch`) and cap input widths to expected content length so the start of a line and its end (or inline status feedback) sit within a single horizontal eye sweep, allocating remaining viewport width to multi-column layout or surrounding whitespace.
- **When** sizing CSS Grid/Flex tracks, full-viewport panes, and text containers, set flexible grid tracks to `minmax(0, 1fr)`, flex children to `min-width: 0`, full-width containers to `width: 100%`, full-height panes to `100dvh`, and text containers to `min-height` (or `max-height` paired with `overflow-y: auto`), and adapt reusable components to their parent slot using `@container` queries on a container with a definite width rather than viewport `@media` queries. *Guardrail*: Never use `100vw` (which includes vertical scrollbar width and causes horizontal overflow), never use `100vh` on full-height mobile panes, never put a fixed `height` on a box holding text, never apply `container-type: inline-size` to a shrink-to-fit element without a definite width, and never set `maximum-scale=1` or `user-scalable=no` in the viewport meta tag.
- **When** positioning controls near viewport edges or pinning (`sticky` / `fixed`) chrome above scrolling content, inset controls from viewport edges by at least `16px` plus `env(safe-area-inset-*)` (declaring `viewport-fit=cover` in the viewport meta tag), give pinned chrome an opaque background surface or a dedicated non-overlapping layout track, set `scroll-padding-block-start` / `scroll-padding-block-end` on the scroll container to match the pinned chrome height, and set `scroll-margin-block-start` on anchored headings so scrolling, focused, or anchored content never collides with, bleeds through, or lands hidden beneath pinned chrome. *Guardrail*: Never float transparent or unbacked text controls directly over scrolling text or imagery, and never park a primary or critical action where resizing to `320px` width, scaling text to `200%`, or opening the mobile on-screen keyboard clips it.
- **When** variable-length content is truncated (`overflow: hidden; text-overflow: ellipsis; white-space: nowrap` for single-line truncation, or `display: -webkit-box; -webkit-box-orient: vertical; -webkit-line-clamp: N; overflow: hidden` for multi-line clamping) or sits past a scroll edge or behind a disclosure, provide a keyboard- and touch-reachable path to the full text (an expand control, detail view, or focus-reachable tooltip) and signal off-screen scrollable content by letting the next item peek `16–32px` past the scroll edge or rendering a disclosure control that states the hidden item count. *Guardrail*: Never rely on a hover-only `title` attribute as the only path to truncated content.
- **When** an interface holds stateful navigation such as filters, search queries, sort order, active tabs, pagination, or expanded detail panels, synchronize that state into URL query parameters so reloading, navigating back/forward, or sharing the link restores the exact view.

## Color Systems and Visual Contrast

Interface color distinguishes surface roles, encodes semantic state, and guarantees legibility across appearances.

- **When** structuring a color system and naming tokens, build palettes from perceptual ramps (1 `neutral` ramp carrying backgrounds/borders/text, 1 `accent` ramp, and only the status ramps the product actually renders, keeping light-end steps `50–200` spaced `0.04–0.05` apart in OKLCH `L`, mid-ramp steps `0.07–0.10` apart, and adjacent steps at least `0.03` apart) separated into two tiers: *Primitives* named by hue and step (`--blue-600`, never referenced in components) and *Semantics* named by role (`--color-bg-surface`, `--color-text-secondary`, `--color-border-subtle`, `--color-accent-solid`); reference only semantic tokens matching the element's role inside components, and assign each hue (treating anything within $15^\circ$ of OKLCH hue as the same color) one meaning across the interface, keeping every status hue at least $15^\circ$ of OKLCH hue away from the accent hue. *Guardrail*: Never write raw color literals (hex, `rgb()`, `oklch()`) or primitive tokens inside components where tokens exist, never borrow a token from another role (such as using a separator/border token for text `color`) because its value matches today, and never define both `--color-primary` and `--color-text-primary` (use `accent` for the brand color and reserve `primary` for hierarchy rank).
- **When** rendering text, icons, or control boundaries against any background (including translucent surfaces, gradients, images, and hover/selected states), ensure the rendered foreground-against-background pair meets minimum contrast: `4.5:1` WCAG 2 (or APCA `Lc 75` for body text, `Lc 60` for labels) for normal text, `3:1` (APCA `Lc 45`) for large text ($\ge 24\text{px}$ or $\ge 18.67\text{px}$ bold), and `3:1` (APCA `Lc 30`) for UI component boundaries and meaningful icons; when a pair fails and color remediation is requested, adjust perceived lightness while holding hue constant and remeasure, and always pair status or meaning carried by color with a second visual cue (an icon, text label, or underline). *Guardrail*: Never let color be the sole carrier of state or meaning, never fix contrast by shifting hue instead of lightness, never place text on an unmeasured translucent/image background without a scrim or worst-region verification, and never put white text on a mid-ramp `500` fill that fails `4.5:1` (use step `600` or Radix step `9` for solid fills).
- **When** declaring wide-gamut colors or gradients, declare an sRGB color value first and place Display P3 `oklch()` values inside `@media (color-gamut: p3)` so sRGB displays never clip adjacent ramp steps into one color, and interpolate gradients in `oklab` by default (switching to `in oklch shorter hue` or adding a midpoint stop when two opposite hues pass through a gray dead zone).
- **When** supporting dark mode, increased contrast (`prefers-contrast: more`), and browser-default surfaces, switch themes through a single mechanism throughout (`.dark` class or `prefers-color-scheme`, paired with `color-scheme: dark` on `<html>` and a matching `<meta name="theme-color">`), lower the accent's chroma by 1–2 steps on dark backgrounds, widen lightness separation between dark surface steps, provide separate `@media (prefers-contrast: more)` overrides for light and dark appearances (widening the lightness gap to the background by at least `0.15` OKLCH `L`), and theme `::selection`, `caret-color`, scrollbars, and link underlines (`text-underline-position: from-font` / `text-underline-offset`) from the system palette. *Guardrail*: Never create a dark theme by mechanically reversing light ramp steps without lowering accent chroma and remeasuring contrast, never mix `prefers-color-scheme` on some tokens with a `.dark` class on others, and never apply a single `prefers-contrast: more` block across both light and dark modes.

## Interactive Control Weight and Accessibility

A control's visual prominence must reflect how likely the user is to take that action next, while every control works across pointer, touch, keyboard, and screen readers.

- **When** constructing controls, navigation, and page structure, follow the stack's encapsulation boundary—if the project encapsulates UI in components, macros, or partials, render feature views from those reusable units and confine raw HTML interactive tags to their internal definitions (alongside page-level structural landmarks `<header>`, `<nav>`, `<main>`, `<aside>`, `<footer>` with distinguishing `aria-label`s when multiple landmarks share a tag, sequential `<h1>–<h6>` headings, and a visually hidden `.sr-only` `"Skip to content"` link targeting `<main id="main">` as the first focusable element when chrome precedes `<main>`); if the project is authored in raw HTML without a component or macro layer, write semantic HTML tags directly with the project's shared CSS classes and tokens—in both cases binding only semantic HTML primitives whose visual rendering is fully governed by project CSS (`<button>` for actions, `<a href>` for navigation that changes the URL so Cmd/Ctrl/middle-click works, `<label>` and `<form>` for inputs) while building any control with a popup, stepper, or custom surface with project styles, ARIA roles, and keyboard handlers rather than browser-rendered widget chrome, and give every interactive element a visual cue distinct from static prose (a background fill, border, underline, or dedicated toolbar zone) while applying `pointer-events: none` (plus `aria-hidden="true"` on DOM elements) to decorative glow/scrim overlays so they never block pointer events on controls beneath them. *Guardrail*: Never write raw HTML interactive controls directly in feature views when the project provides a component or macro for them, never use native browser-chrome widgets or OS dialogs whose visual surface, popup, or sub-controls cannot be styled through project tokens (`<select>`, `<option>`, `<input type="number" | "date" | "time" | "datetime-local" | "month" | "week" | "color">`, unstripped `<input type="checkbox" | "radio" | "range">` without `appearance: none`, native `title` tooltips, or `window.alert` / `confirm` / `prompt`), never attach `onClick` to a `<div>` or `<span>`, never style a static badge identically to adjacent buttons, never put `aria-hidden="true"` on a focusable element or its ancestor, never use `0px` dimensions on `.sr-only` (use `1px` with `clip-path: inset(50%)` and `white-space: nowrap`), and never omit `alt` on `<img>` (`alt=""` for decorative images, meaning for informative images, action/destination for functional images).
- **When** sizing touch/pointer targets and spacing adjacent controls, provide a hit area of at least `24×24` CSS pixels (targeting `44×44px` on touch and `40×40px` on desktop; when the visible glyph is smaller, expand the hit target with a centered `::after` pseudo-element on the `<button>` or wrapper), set `touch-action: manipulation` on interactive controls, and separate adjacent bordered/filled controls by at least `12px` and visible glyphs of adjacent borderless text/icon controls by at least `24px`. *Guardrail*: Never place a hit-area pseudo-element directly on `<input>`, and never allow expanded hit areas of adjacent controls to overlap.
- **When** implementing keyboard navigation and focus indicators, provide a keyboard path for every pointer interaction matching the visual/DOM reading order (using only `tabindex="0"` to enter the natural tab order and `tabindex="-1"` for programmatic focus; using `roving tabindex` on composite widgets like tabs, menus, toolbars, and radio groups so the widget takes one Tab stop and arrow keys move inside it, or `aria-activedescendant` when focus stays in a combobox input), and render a `:focus-visible` ring with at least `3:1` contrast against every adjacent surface it crosses (preferring the browser ring with `outline-offset: 2px` or a verified `2px solid` focus token, and `:focus-within` on compound input wrappers). *Guardrail*: Never use a positive `tabindex` (`1`, `2`...), and never set `outline: none` or `outline-none` without a verified `:focus-visible` replacement.
- **When** multiple actions appear in the same decision scope, assign the high-contrast solid fill to at most one primary action (putting the accent color on the background, not the label); demote secondary actions to outlined, subtle, or text treatments, and move secondary actions behind a menu once there are more than three. *Guardrail*: Never place two high-contrast solid-filled peer buttons side by side in the same control group, and never use accent-colored text on a neutral button to signal primary emphasis.
- **When** designing a data-mutating or destructive action, choose between immediate execution with undo and pre-action confirmation based on reversibility and blast radius: if the action can be reversed and is performed routinely, execute it immediately and surface a persistent toast containing an `Undo` action; if the action cannot be reversed, affects other users, or destroys multiple items at once, style its trigger in the primary view with low-contrast treatment and require a confirmation dialog whose title and confirm button both state the exact verb and target object, whose body states exactly what is permanently lost (including item counts and affected users where applicable), and which focuses the least destructive button when opened (for high-impact shared containers, require the user to type the object's name and keep the confirm button disabled until the input matches). *Guardrail*: Never title a confirmation dialog `"Are you sure?"`, never label confirmation buttons `Yes`/`No`, and never execute an irreversible destructive action immediately without confirmation.
- **When** a control is unavailable, use native `disabled` (or `aria-disabled="true"` with pointer/keyboard activation blocked in code when keeping the control discoverable in the tab order is intentional) and state why the control is unavailable and how to unlock it in visible text beside the control. *Guardrail*: Never attach a tooltip to a natively `disabled` control (which suppresses pointer events and leaves the tab order, making the tooltip unreachable by keyboard or touch), and never set both `disabled` and `aria-disabled` on the same element.
