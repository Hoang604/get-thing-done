# Forms, Inputs, Selection Controls, and Validation

## Labels, Input Configuration, and Field Sizing

- **When** rendering any form control, bind a persistent visible `<label for="...">` matching the control's `id` (or wrap `<label>` around binary checkbox/radio/switch controls and their text so both share one continuous hit area), mark required fields with native `required` plus a visible indicator explained once per form, and expose format or length constraints up front in persistent helper text linked via `aria-describedby`. *Guardrail*: Never use `placeholder` text in place of a visible `<label>` or put required-format instructions inside a `placeholder` (placeholders show only an example value or `"Search…"`).
- **When** configuring `<input>` attributes inside a `<form>`, set a descriptive `name`, set an accurate `autocomplete` token (`name`, `given-name`, `family-name`, `email`, `tel`, `street-address`, `postal-code`, `country`, `cc-number`, `cc-exp`, `cc-csc`, `username`, `current-password`, `new-password`, `one-time-code`, or `autocomplete="off"` on non-credential domain fields that trigger false password-manager prompts), pair `type` and `inputmode` to summon the right mobile keyboard without browser-injected spin buttons or scroll-wheel value changes (`type="email"`, `type="url"`, `type="tel"`; `type="text" inputmode="numeric"` for integers, OTP/PIN, and card numbers; `type="text" inputmode="decimal"` for decimals and currency, adding explicit `<button>` steppers only when stepping helps the task), and set `spellcheck="false" autocorrect="off" autocapitalize="off"` on emails, codes, usernames, and identifiers. *Guardrail*: Never use `<input type="number">`, never block `paste` (`onPaste` + `preventDefault`) on any field including passwords and OTP codes, and never set `autoFocus` on mobile viewports.
- **When** sizing form fields on wide viewports, match field width to expected value length (narrower for short-value fields like postal codes, OTP codes, dates, and quantities than for long-value fields) so the start of a field and its end or inline status feedback sit within a single horizontal eye sweep, or lock stacked fields to the form's shared column grid. *Guardrail*: Never stretch short-value inputs across the full width of a wide desktop viewport, and never let stacked text inputs vary in width based on their label lengths.

## Submit-Time Validation and Unsaved-Change Protection

- **When** validating user input, keep the submit button enabled, accept free text, and `trim()` leading/trailing whitespace (added by autofill or text expansion) before validating; on submit, if validation fails, block the request, mark each failing field `aria-invalid="true"` (removing it once fixed), render a positive instruction stating how to satisfy the requirement beside the field with an icon or text cue linked via `aria-describedby`, and move focus to the first invalid field. *Guardrail*: Never disable the submit button (`disabled={!isValid}`) to gate validation before the user submits, never block typing or filter characters per keystroke while the user types, and never signal an invalid field with a red border alone.
- **When** a form holds unsaved user edits (`dirty state`), warn before browser tab close or route navigation (`beforeunload` and router navigation guards), and ensure controlled inputs (`value` paired with `onChange`, or `defaultValue` for uncontrolled inputs), re-renders, and SSR hydration never reset typed characters or steal focus from the active field.
