# Internationalization (i18n), Bidirectional (RTL) Layout, and Change Review

Apply the rules below when the interface supports multiple locales, renders bidirectional (LTR/RTL) user content, or when modifying/reviewing an existing codebase or diff.

## Internationalization, Locale Formatting, and Logical Layout

- **When** writing direction-dependent CSS layout and icon rules, use logical properties (`margin-inline-start`, `padding-inline-end`, `inset-inline-start`, `border-inline-end`, `float: inline-start`, `border-start-start-radius`, `text-align: start`) instead of physical `left`/`right` (reserving physical `left`/`right` only when pairing with physical `env(safe-area-inset-left/right)` alongside a `[dir="rtl"]` override, and adding explicit `[dir="rtl"]` overrides for `translateX` and `background-position`), mirror progression sequences (step indicators, progress bars, star ratings) so they fill from the leading edge in RTL, and under `dir="rtl"` flip (`scale: -1 1`) only icons whose meaning represents reading direction or navigation progression—analyzing composite icons part by part so a directional base glyph flips while an attached badge or slash overlay keeps its position. *Guardrail*: Never flip brand marks, checkmarks, icons whose orientation reflects clockwise time or right-handed physical objects, or media playback controls in RTL, and never apply two flip mechanisms to the same icon.
- **When** sizing text containers for localization, size buttons and labels with `max-width: 100%`, `min-height`, and `flex-wrap: wrap` on control rows so the layout absorbs `30–40%` translation length expansion without clipping or truncation. *Guardrail*: Never put a fixed `width` or `height` on buttons or text labels.
- **When** constructing translatable messages and formatting locale-dependent values, write each message as a complete sentence with placeholders (using ICU MessageFormat or `Intl.PluralRules(locale)` for plural categories), format all dates, numbers, currencies, units, relative times, and conjunction lists through `Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.RelativeTimeFormat`, and `Intl.ListFormat` with the user's locale (including locale-aware digits and calendars where applicable), set accurate `lang` and `dir` attributes (allowing paragraphs of three or more lines to align to their own script's direction), wrap mixed-direction user values (names, numbers, URLs) in `<bdi>`, mark brand names, code tokens, and identifiers with `translate="no"`, and preserve Zero-Width Non-Joiner (`U+200C` in Persian/Kurdish) while treating Arabic/Persian Yeh (`ي`/`ی`) and Kaf (`ك`/`ک`) variants as equivalent in search and validation. *Guardrail*: Never concatenate sentence fragments around variables (`"You have " + n + " new messages"`) or use binary plural checks (`n === 1 ? "" : "s"`), never join localized lists by hand with `", "` and `" and "`, never reorder digits manually, and never detect language from IP address instead of `Accept-Language` / `navigator.languages`.

## System Recon, Blast-Radius Expansion, and Review Reporting

- **When** modifying or reviewing an existing project, inventory the project's framework, styling system, component library, design tokens, interface documentation, and existing translation strings first, and write every fix in the project's established notation, tokens, and vocabulary; before restructuring an existing color palette, collect all color literals across the codebase, sort by perceived lightness within each hue family, collapse near-duplicates within `0.02` OKLab $\Delta E$ into the most-used survivor, map each survivor to a semantic role, and present the inventory before mutating screens outside scope. *Guardrail*: Never scatter a new color notation (such as an isolated `oklch()` literal in a hex codebase), a new dependency, or a new synonym into a project unless a migration is in scope.
- **When** reviewing a code change (diff, commit range, branch, or pull request), keep the review read-only without mutating the working tree unless asked to implement fixes, read the entire diff before forming findings, inspect the removed (`-`) side of every hunk to flag any deleted attribute, element, token, or copy that removes a guarantee required by `SKILL.md` or `references/*.md`—after clearing equivalent replacements that preserve or upgrade the guarantee (such as `aria-label` replaced by `aria-labelledby` pointing at visible text, explicit `role` or `tabindex="0"` dropped because a `div` became a native focusable element, `outline` replaced by a `:focus-visible` `box-shadow` ring, physical properties replaced by logical properties, color literals replaced by semantic tokens, or inline strings moved into a locale catalog)—expand the review scope from changed files to the surfaces that consume them (one hop to direct importers for components, two hops for design tokens and shared primitives, ordered by route entry points first, then importer count, then directory proximity, explicitly naming any consumers left uninspected), and check new components or variants for missing interaction or lifecycle states (hover, focus, active, disabled, loading, empty, error, narrow-width, and localization).
- **When** formatting an interface review report, consolidate findings that share a root cause (such as a shared token or component) into a single row listing every `path/to/file:line` location, classify each change-review finding by cause as `Introduced` (created by the change), `Regression` (weakened something previously compliant), or `Pre-existing` (present before the change and not worsened by it, reported in a separate section), rank severity by user impact (`HIGH` for any defect that blocks a task, risks data loss, hides content or controls from assistive technology or keyboard navigation, clips or overlaps at `320px` width or `200%` zoom, fails required contrast, or carries state/meaning through color or motion alone; `MEDIUM` for defects that harm comprehension, efficiency, adaptability, or system consistency; `LOW` for isolated polish), list executed verification checks separately from checks marked `Not verified` (with the reason), and end with `Block` if any `HIGH` finding (or `HIGH` `Introduced`/`Regression` finding in a change review) remains, or `Approve` otherwise (naming any uninspected domains or consumers in the verdict line).
